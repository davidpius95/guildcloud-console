## Working discipline to keep following

1. **Always re-read the plan's exact text from the docx before architecting
   anything** — not from a summary. This surfaced real requirements
   (§17's explicit "choose and document the tenancy model" instruction)
   that a paraphrase would have missed.
2. **For anything that changes a live standing system** (an ACL policy,
   provisioning a VM, anything with real capacity or reachability
   consequences): write a Decision Record in `docs/decisions/` proposing it
   first. If it's consequential (capacity commitment, changes what's
   reachable), get explicit sign-off before applying — don't take a general
   "continue" as authorization for a specific irreversible action.
3. **Re-verify live state after every change** — never infer success from a
   call returning without error. This project already caught real failures
   this way (an empty API response that looked like success, a wrong GitHub
   Action version, a PBS permission bug) that would have shipped silently
   broken otherwise.
4. **Write a dev log entry** (`docs/dev-log/`) after each real chunk of
   work — what changed, why, what was verified, what's still open. This
   file is itself an example of the pattern.
5. **Confirm repo sync explicitly**, don't assume it — `git fetch` +
   compare `origin/main..main` and `main..origin/main` both ways.
6. Load the relevant skill under `.claude/skills/` for the kind of work
   being done — see `.claude/skills/README.md` for the index. They're
   grounded in this project's real state, not generic.
