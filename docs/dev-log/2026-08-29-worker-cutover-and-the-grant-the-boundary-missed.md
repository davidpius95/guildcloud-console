# 2026-08-29 (night) — both workers off the service-role key, and the grant the boundary missed

Task 7 slice C is done. Guild-A and Guild-B both authenticate to the control
plane with a cluster-scoped ES256 worker token; neither holds the Supabase
service-role key. Getting there broke a production cluster first.

## The cutover itself

The legacy HS256 JWT secret was exposed earlier in the day, so the original
minting path — sign with the project's JWT secret — was dead before it was used.
`mint-worker-token.mjs` gained an ES256 mode taking a key generated by
`supabase gen signing-key` and imported as a standby key, so worker tokens are
signed by a key this project holds and survive revocation of the legacy secret.

**Standby keys verify. Rotation is not required, and that is worth knowing**,
because rotating changes which key signs every user auth token Supabase issues.
The docs say standby keys appear in the JWKS but not whether PostgREST accepts
them, so it was tested rather than assumed: a token minted under a
freshly-imported, never-rotated standby key (`kid 3cf66c3f-…`) posted to
`worker_heartbeat` returned **HTTP 204**. The runbook now stops at standby.

## The boundary was missing two grants

The Guild-B cutover completed, reported healthy, and **broke the cluster**.

```
{"ok":false,"stage":"publish_snapshot_idle","error":"could not read vault secret
 proxmox_guild_b_site_worker_token: permission denied for function get_vault_secret"}
```

Task 7 enumerated the worker's *table* access and replaced it with `worker_*`
RPCs. It missed that the worker also reads Vault: `get_vault_secret` for its
Proxmox API token, `set_vault_secret` for per-instance SSH passwords. Both were
granted to `service_role` and to the old per-cluster role `site_worker_guild_a`,
never to `guildcloud_site_worker`. Removing the service-role key removed the
Proxmox credential with it.

Guild-A hit the same wall two minutes later. Both were restored by granting the
two functions to the worker role; each cluster's next cycle came back clean.

That grant is **deliberately weaker than the rest of the boundary** and is a
stopgap. `get_vault_secret` takes an arbitrary secret name, so a worker holding
it can read any secret including the other cluster's Proxmox token — the exact
per-cluster isolation Task 7 exists to enforce. It is still strictly less
privilege than the service-role key it replaced, which could read every secret
*and* bypass RLS on every table, so granting was better than rolling back on both
axes. The scoped replacements — `worker_get_proxmox_credential()` and
`worker_set_instance_ssh_password()`, neither taking a caller-supplied name —
should supersede it.

## The health check is the real bug

`--health` reported `controlPlaneReachable: true` throughout, on both clusters,
while nothing worked. It only calls `controlPlane.heartbeat()`, and
`worker_heartbeat` needs no Vault.

This is worse than the missing grant. `cutover-worker.sh` uses `--health` as its
rollback gate, so the automatic rollback that exists precisely for this did not
fire — on either cluster. And it is what let a successful-looking cutover be
reported while Guild-B could not reach Proxmox at all.

A health check that cannot fail the way production fails is not a health check.
It should exercise every credential the worker depends on: read the Proxmox token
*and* make one authenticated call with it, and the same for Tailscale on whichever
worker holds housekeeping.

The missing grant was a ten-minute outage. The health check is why nobody noticed
for six of those minutes, and why it would have happened again on the second
cluster.

## A smaller finding

Every Guild-B cycle logs
`worker_get_tailnet_desired_state failed: worker does not hold the tailnet
housekeeping role`. That is the boundary working correctly — Guild-B is not the
housekeeper — but the worker calls the RPC anyway rather than checking
`tailnet_housekeeping` on its own identity first. Harmless, and the work happens
on Guild-A, but it means every cycle on the non-housekeeping cluster reports a
failure it should never have attempted.
