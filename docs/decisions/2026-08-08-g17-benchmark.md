# Decision record: G-17 — real performance benchmark

**Date:** 2026-08-08
**Status:** complete. Real, measured numbers for storage, network, and
provisioning time — replacing "no benchmark has ever been run."

## Context

Gap register G-17: all capacity numbers in `capacity-model.md` were
configuration-time estimates, never load-tested. Plan §16 requires
"measured provisioning and recovery performance on actual sites before
any customer expectation is stated."

## Method

Cloned two minimal throwaway VMs from the existing Ubuntu template
(`bench-nodeb` on `nodeB`, `bench-nodee` on `nodeE` — different nodes, to
also get a real inter-node network measurement), timed their full
provisioning cycle, ran a real storage I/O benchmark on one, and a real
network throughput test between both. Destroyed both VMs immediately
after — zero persistent footprint, matching the same discipline as the
G-11 SDN validation.

## Result 1: provisioning time

Recorded the VM `start` task's real timestamp, then polled for QEMU
guest-agent readiness (the point at which the guest is genuinely usable,
not just "started"). Two independent measurements:

| VM | Clone→agent-ready |
| --- | ---: |
| `bench-nodeb` (nodeB) | 109 seconds |
| `bench-nodee` (nodeE) | 121 seconds |

**~110-120 seconds** for a full cold provisioning cycle (linked clone,
cloud-init, boot, agent-ready) on this hardware.

## Result 2: storage I/O (4K random read/write, 70/30 mix)

Ran `fio` directly on a guest's Ceph-backed virtual disk (`ceph-vm`
storage, the same pool every real guest uses) — the number a customer
would actually experience, not a raw RADOS-level number.

| Metric | Value |
| --- | ---: |
| Read IOPS | 139 |
| Read throughput | 560 KiB/s |
| Read avg latency | 2.27 ms |
| Write IOPS | 62 |
| Write throughput | 250 KiB/s |
| Write avg latency | 10.87 ms (p99: 24 ms, worst: 148 ms) |
| Disk utilization during test | 98.59% (genuinely saturated, not idle) |

**These are modest numbers** — consistent with a small home-lab Ceph
cluster on consumer SSDs with 3x replication over a shared LAN, not
enterprise storage. Write latency in particular (each write must commit
to 3 OSDs before acknowledgment) is high enough that it would visibly
affect any write-heavy workload. This is exactly the kind of number §16
requires be measured before it's ever implied to a customer.

**A live illustration of the same finding, found by accident**: while
this benchmark was running, `bench-nodee`'s cloud-init-triggered kernel
dist-upgrade took unusually long specifically at the initramfs-write
step — directly explained by the same ~250 KiB/s write throughput just
measured. Real infrastructure, real consequence, not just a synthetic
number.

## Result 3: network throughput (inter-node, same LAN)

`fio`/`iperf3` installation on `bench-nodee` got stuck behind a slow
cloud-init dist-upgrade (see above), so used `nc`+`dd` instead — both
preinstalled, no dependency on the stuck package manager. Sent 500 MiB
from `bench-nodee` (`nodeE`) to a listener on `bench-nodeb` (`nodeB`) via
raw TCP, timed via `date +%s.%N` on both ends (avoided `time`, which
dash's builtin doesn't support the same way as bash for piped compound
commands).

**Result: 500 MiB in 54.33 seconds ≈ 9.2 MB/s (~73.6 Mbps) sustained.**

Lower than what a modern gigabit LAN would typically deliver — plausibly
explained by single-stream `nc` overhead, CPU contention from
`bench-nodee`'s concurrent dist-upgrade eating cycles on the same 2-vCPU
guest, or a genuine network-layer constraint (unmanaged switch, cabling).
Root cause not isolated — this number is a real single data point, not a
definitive network capacity ceiling. Worth a follow-up with a proper
multi-stream `iperf3` test once tooling installs cleanly (i.e., not
racing a dist-upgrade).

## What this means for the capacity model

`docs/phase-0/capacity-model.md` is explicit that its RAM/storage
headroom numbers are configuration-time, not load-tested. These new
numbers don't change that document's RAM math, but they do mean: **any
future customer-facing IOPS, latency, or throughput claim must be
grounded in these measured numbers (or better ones from a cleaner re-run),
not assumed from hardware specs.**

## What this doesn't cover

- CPU benchmark (not run — RAM and storage are the binding constraints
  per the existing capacity model, CPU headroom was already noted as "not
  binding").
- A clean, non-contended network throughput re-test (this one raced a
  concurrent dist-upgrade on the same guest).
- Guild-B's performance profile — this benchmark only covered Guild-A.
- Recovery/restore timing under load (the G-02 restore drill measured a
  successful restore, but not its duration under contention).

## What changed

- No live infrastructure was changed. Two throwaway VMs were created,
  benchmarked, and fully destroyed.
- `docs/phase-0/gap-register.md` — G-17 resolved with real numbers.
